# Rust account admission core

This standalone crate implements the serialized account-admission and durable reservation portion of Baal's backend. It does not open sockets, load credentials, read the production runtime, create keys, or submit/cancel orders. The current Node collector remains the sole account client. No live configuration is changed by building or running this crate against an offline directory.

Source ports: `live-paper/transport-runtime.mjs` (`ReadClient` completion pacing, pre-network fence and cooldown), `live-paper/transport-network-budget.mjs` (1000 ms reads / 2500 ms writes), `feed/runtime.mjs` (`retryAfterMs`), and `execution/transport.mjs` (immutable intent/key bodies and two authority checks). This is a component migration, not a replacement for the execution ledger, API response validation or authenticated ownership checks.

Build and test with `./build.ps1 -Test`. It uses the existing task-local Rust toolchain and a standalone locked crate; it does not edit the root Rust package. `node data/rust-account-queue-parity-20261005.mjs` compares the compiled core with the actual Node `ReadClient` under offline HTTP substitutes. The generated JSON records four matched pacing/cooldown scenarios. The Rust unit suite additionally covers 4,000 deterministic rolling-window admissions, scoped lock loss, queue serialization, torn journals, clock regression, crash restoration and uncertain writes.

Run the executable as `baal-account-queue.exe --offline-jsonl DIRECTORY SCOPE TOKEN`. DIRECTORY must be a new or previously owned **offline** test directory; TOKEN is a process identity nonce, not an API token. Each input is one JSON object followed by a newline; each output is one JSON object with `ok` and either `result` or `error`. The binary flushes each output only after the state append is written and synced. Unknown fields are rejected.

The commands are:

- `admit`: requires `scope`, integer epoch `now`, unique `request` and `write`. Returns `admitted:false, wait_until` when paced; the caller advances/waits and resubmits that unchanged logical request. Every read/write shares one active slot. A write also requires `authorized`, `permit_valid`, `lease_valid` all true, plus `binding:{intent,key,payload_hash}`. The lowercase 64-character payload digest must identify the exact canonical operation, endpoint, scoped body and idempotency key computed by the trusted adapter.
- `network`: requires the admitted request identity; writes must present the same binding and repeat all three validated fences. The durable transition precedes the external HTTP operation. Duplicate network transitions are rejected.
- `complete`: requires the admitted request identity, `outcome` (`success`, `rejected`, `unknown`, or `not_sent`), optional HTTP `status`, raw `retry_after`, and validated `api_code`. It preserves completion pacing after body processing. A dispatched operation cannot subsequently be declared `not_sent`. The adapter must classify ambiguous write acknowledgments as `unknown`, including malformed or semantically unverified success bodies; a JSON HTTP response alone does not prove canonical order acceptance.
- `reconcile`: exact unknown binding plus independently verified `reconciled`, `lease_valid`, `permit_valid`. It clears the global unknown-write fence but never permits a same-intent replacement/retry; original key/body bindings remain reserved. Read-only reconciliation remains possible while an unknown write exists.
- `status`: returns the offline admission state. It contains opaque request identities and payload hashes, never credentials or account positions.

Booleans in this protocol are **not authorization**. Only a trusted in-process adapter executing the existing Node owner/STOP/lease/permit validators may produce them. Do not expose this CLI as a network service or connect arbitrary callers. Before live integration, the parent must preserve the real execution ledger, documented API allowlists, scoped contract/exchange validation, owned-order checks, fresh reconciliation, activation bounds and exact response/idempotency semantics. Canonical hashing and those validators are not implemented by this admission crate.

The core explicitly enforces at most 60 reads and 24 writes in every **inclusive** rolling 60-second window, conservatively waiting until oldest admission + 60,001 ms. Existing Node pacing tests allow boundary totals of 61/25; this stronger boundary is intentional, so throughput is not claimed identical there. Read/write admission reservations count even when a later authority fence prevents network dispatch. Retry-After respects 429's 60-second and 503's 10-second minimum; numeric overflow or backward wall time permanently requires manual review. `REQUEST_IN_FLIGHT` adds 90 seconds to the shared cooldown.

Every state record has a sequence and SHA-256 predecessor chain. On restart, admitted writes are uncertain even if the network fence was never reached, so replacements fail closed. A dispatched interrupted read holds 21 seconds from its last durable clock, covering the existing 20-second HTTP timeout plus pacing. Torn/unterminated/corrupt journals, unknown schema, other scope and lock loss fail closed; no journal repair or automatic stale-lock takeover occurs. An abrupt process death leaves its lock. The owning operator must prove the process is gone and reconcile writes before removing it; lock timestamps are never authority.

The lock is local exclusive-file ownership, not a distributed account lease. The current one-account-client constraint remains necessary. Hash chaining detects accidental corruption; it is not protection against a local attacker able to rewrite the entire directory. Full-state appends are conservative and grow with lifetime intent history; a bounded compaction protocol preserving all bindings is future work. Files are synced before replies, but Windows directory-entry/power-loss durability and inherited restrictive runtime ACLs require explicit deployment integration and fault testing. No absolute power-loss or live speed claim is made.

Publish source, Cargo.lock, this README, the build script and offline parity files. Do not publish `target/`, binaries, journals, lock files or production runtime data.
