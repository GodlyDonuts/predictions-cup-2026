# Faster selection with independent case generators

`EvaluationBatch` now has an opt-in `batch_action_heads` mode. It batches the conditional neural heads as well as encoding, while each evaluation case retains its own random generator, hidden state, virtual clock, source boundaries, API budget and ledger. Variable-length market categories are trimmed before each case's draw. Categorical sampling uses the original Torch multinomial operation; Beta sampling uses the same installed Dirichlet kernel with an explicit generator. There is no alternate distribution or new action filter.

The installed CPU/CUDA kernels pass exact sample and final-generator-state comparisons against the original distribution methods. End-to-end fixtures cover unequal entity counts, different completion times, all four raw-policy architectures, stochastic/deterministic paths and the full joint-memory actor. Caller RNG is preserved. Teacher forcing and default training sampling do not use this optional sampler; likelihood and action support remain unchanged. The Dirichlet operation is a private Torch API: unsupported runtimes fail rather than silently changing algorithms. Finite GPU evidence must record the actual Torch version.

To select this mode in a new frozen experiment, explicitly set both `batched_evaluation=true` and `batched_evaluation_action_heads=true`. Invalid combinations fail before output creation or data loading. Each case reports `batch_encoding_and_action_heads_case_local_generators`. Old defaults remain available for reproduction. Numerical matrix batching is not an all-future bitwise equivalence guarantee; fixtures/finite paired measurements bound the evidence actually checked.

The existing `evaluation_benchmark` command and CLI remain intact. The separate `evaluation_heads_benchmark` compares full serial execution, batched encoding with serial heads, and batched encoding/heads in balanced forward/reverse order. It requires an exact same-dataset checkpoint and inspected development configuration, shared measured compute cost and independent case seeds. Optional paid **simulated** book priming measures delivered full-depth data without real API requests. It checks account/liquidity/order/fill state, virtual clocks, budgets, discrete actions, statuses, fraction/recurrent tolerances, final case RNG and unchanged weights. It cannot open a final test or claim full-episode ROI.

Example: `python -m moloch.learning_actions.evaluation_heads_benchmark --config <private-config> --checkpoint <exact-checkpoint> --checkpoint-sha256 <sha> --output <new-private-output> --steps 64 --prime-books -1`. Minus one primes **all** available SIG book-request targets and reports actual per-case read/book counts. The first checked probe requested eight book targets per case and refused an opening scope with no book targets yet; the second all-target setup confirmed this was a source-timing issue. Both failures are retained with no timing result inferred. An exact key audit found that the first selection window opens before its first SIG-book event, while the second window opens with237book targets. Benchmark setup now waits on original source events until a target exists, retains the real virtual timestamps and reports that warmup separately; it never manufactures a quote. It fails if the role ends first. Priming/setup is outside the timed decision chunk, and does not change the live training/evaluation calendars.

The initial full-size32-step draft probe succeeded and motivated a checked, primed-data measurement; draft timing is not published as qualified runtime evidence. The240-check action suite passed before the final strict profile guard, and17 focused checks passed after it, including the new early guard. GPU017 and CPU002 continue using their original frozen source. This code has not been hot loaded or presented as already accelerating those workers. No new account client/request, held-out test use, production change or independent profitable checkpoint is established by this work.

The stronger all-book64-step checked probe **failed strict full-record equivalence**. A separately retained instrumented replay localized the first mismatch to requested order quantities in two cases; cash, holdings, fills, book/liquidity state, clock and finance revision matched. One request differed by59shares around1.006billion shares, with the same already-sized executable remainder. Even the old batched-encoding mode can change floating-point head inputs relative to full serial computation. Exact primitive-kernel RNG equivalence does not imply bitwise-identical neural trajectories.

The benchmark therefore keeps strict comparison as its default. An explicitly labeled `--allow-sized-request-differences` measurement may report requested-quantity differences only when cash, positions, realized accounting, fees, fills, books/depletion, clocks, complete budgets, case RNG, order IDs/price/side/expiry and actual executable remainders match. Both requested quantities must already exceed that identical remainder. It does not modify any actual order, ACK, local-memory field or action; it records the differing requests and sets `fullOrderRecordsIdentical=false`. Any other mismatch fails. This is a bounded performance observation under a declared numerical mode, **not complete behavioral equivalence** or permission to reuse prior evaluation scores. Future decisions may react to requested-quantity metadata; a new frozen evaluation source/profile is required before comparing outcomes.
