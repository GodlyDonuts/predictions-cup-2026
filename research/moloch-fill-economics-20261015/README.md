# Actual-fill economics diagnosis — October 15

This offline Python 3.10+ tool diagnoses the existing Moloch bank. It does not call the API, manage a process, submit orders, select a strategy, or establish profitability. Scope is the source/main execution task [#120](https://github.com/GodlyDonuts/predictions-cup-2026/issues/120), parent claim `6199775354`; source base `ebae6ff8`. The parent execution owner alone obtains private snapshots and operates production.

```sh
python3 research/moloch-fill-economics-20261015/analyze.py \
  --report ~/apps/moloch/fill-economics-20261015/private-report-snapshot.json \
  --adoption ~/apps/moloch/fill-economics-20261015/private-adoption.json \
  --output ~/apps/moloch/fill-economics-20261015/public-aggregates.json
python3 -m unittest discover -s research/moloch-fill-economics-20261015 -v
```

Both source files stay private. The report input is the native envelope with `report`, `orders`, `fills`, and `sequence`; the adoption input is the actual `actual_position_adoption` event or a journal row containing it as `event`. Inputs are read only. Output cannot overwrite either source path. Each public result includes SHA256 of the exact input bytes, aggregate counts, public exchange/market IDs, per-market P&L, closed-lot win/loss counts, exit mix and remaining cost. It omits raw order/fill/lot IDs, account/profile fields, source paths, receipt hashes, titles and timestamps. Errors use fixed codes rather than echoing private payloads. Do not commit the source snapshots. No private production snapshot was used for the synthetic tests.

The bank's recorded `fills` array is authoritative order. No global execution-time sorting or deduplication is performed. Duplicate fill IDs, changed bindings, absent order joins, overfills and per-order `filled` mismatches reject the analysis. The first fill's observation clock must be at or after adoption; every subsequent observation must be monotonic and bounded by the report clock. Executions may be tied or arrive in reverse order; those cases are retained and counted. RFC3339 clocks retain nanoseconds, including the official seven-digit fractions.

The replay follows `Wallet::buy_fill_exact` / `sell_fill_exact` in `moloch/native/src/lib.rs` and `consume_inherited` / adoption in `engine_live.rs`:

- Adopt the verified signed-side opening FIFO lots at their lot-derived entry principal. Verify quantity, lot order, lot principal and reported-basis discrepancy metadata. Historical acquisition clocks do not become new trading fills. Reported basis discrepancies remain labelled; this is not official account realized P&L.
- Each actual BUY appends its lot, expenses its fee, and immediately redeems the minimum YES/NO quantity FIFO for one SUSQie per pair. SELL consumes its own-side FIFO lots. Exact decimal amounts become integer millionths; binary floats are rejected.
- Inherited gross uses a SELL's actual price, or `1 - actualBuyPrice` for an opposite-side BUY. New trading realized is total realized minus inherited gross. All fees, including inherited liquidation fees and fees on still-open new lots, remain in new trading realized, matching the native report.
- Require the exact ending FIFO quantity/price sequence, total owned cost, realized, inherited gross, new trading realized and fees to match the report. No mark or estimated liquidation value is attached to remaining inventory.

The source report does not expose seed policy. Initial wallet cash is therefore **derived** as `report.cash + report.ownedCost - report.realized`. Adoption withdraws the opening inventory cost from that seed before actual fills; the replay then verifies the same accounting identity and ending cash. This cash check is conditional on the source's seed identity, not independent verification of initial cash or a fresh official cash receipt. A consistent shift to both source cash and derived seed cannot be detected without a separate immutable seed proof. The tool neither verifies the full bank hash chain nor claims that source hashes alone authenticate the account.

Each actual BUY fill is a new-lot cohort, including partial fills on one order. Closing fragments retain FIFO cohort membership. `fullyClosedGrossWins/Losses/Flat` concern fully closed BUY lots before fees; partially closed lots remain separate. All reported P&L totals are exact including fees, but fees are not arbitrarily divided among lot fragments. For a new/new opposite-buy pair, the older outgoing lot receives the pair's gross spread and the incoming paired lot receives zero gross; this convention conserves P&L without counting it twice. A first new entry after inherited-only liquidation is not counted as a reentry; later BUYs after a new-trading market has become flat are.

Exit metadata is joined from the original order, since actual fills do not carry `inventoryExitReason` or `executionStyle`. The exit mix separates inherited/new, SELL/opposite-buy redemption, `maximumAge`/unspecified and `inventoryAON`/unspecified. New-lot holding age uses **actual closing execution minus actual opening execution**, with an inclusive 600,000ms maturity boundary. A single maximum-age order can close both matured and fresh FIFO lots; the output reports both. Negative ages from delayed observations are labelled execution-clock reversals, never silently sorted or presented as ordinary holding times. Entry observed after closing execution and observation delays of at least ten minutes are counted separately. A `maximumAge` label is evidence of the order's trigger, not a claim every consumed lot had matured or that a later fill was advantageous.

Tests independently specify small ending ledgers: mixed inherited/new partial FIFO exits with fees; opposite-side immediate payout; new/new pair conservation; reverse/tied execution clocks; fresh and mature lots in one forced exit; multiple partial fills on one order; reentry after flattening; negative NO holdings and discrepant basis; pre-adoption fills; inconsistent quantities/amounts/joins; all 86 distinct records retained; nanosecond clocks and public-output redaction. Run on a frozen report/adoption pair; do not edit live runtime or bank files to obtain a passing diagnosis.
