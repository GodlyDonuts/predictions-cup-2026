# Shared paired execution ledger

This pure ledger connects canonical per-order journals to a shared allocated cash balance, both contract inventories and cumulative purchase usage. It has no API or dispatch capability. Returned states are proposed transitions that the production host must durably journal and replay under the existing account owner lease before using them. This component is not currently connected to production dispatch.

The fixed initial allocation is 25 SUSQ, with 25 maximum owned basis, 5 maximum order/orphan principal, 100 cumulative nominal purchases, 6 shares and a 30-second maximum order lifetime. Closing a position does not replenish cumulative purchase usage. Every possible partial fill is checked against the orphan cap, using the most expensive held shares as a conservative bound. Covered NO sells cannot canonicalize into unintended complement buys. Unmatched entry inventory sizes the second buy to actual reconciled first-leg shares; unmatched exit inventory must be sold before reopening. No second intent may start while another is unresolved, and its full reservation remains held until reconciliation.

An original complete account snapshot keeps unrelated signed holdings external. Fresh positions and no open orders must agree before reservation. Selected exact-money receipts must bind the tournament ID/slug, documented GET route, joined status and snapshot interval. Snapshots after terminal evidence must match its exact nominal cash delta and all expected signed positions, while unrelated holdings remain unchanged. Complete bounded account activity must contain precisely the current order's fills, with no collateral or unrelated economic events. The canonical projection is recomputed from the original shared-cash baseline before application. Cash plus owned FIFO basis must equal initial allocation plus realized result after every accepted close, including losses.

Source hashes bind supplied evidence; they do not authenticate arbitrary caller assertions or manufacture API completeness. The production adapter still needs to establish complete actual activity coverage, bind realtime NO fill convention and exact acknowledgements, and verify cash/collateral semantics. The REST transaction schema does not expose a documented order/fill ID mapping, so its rows cannot be invented into this normalized fill window. Terminal projections and successful tests never grant execution authority. Fresh book/rule/settlement compatibility, package margin, owner/admission fences and durable whole-portfolio persistence remain host requirements.
