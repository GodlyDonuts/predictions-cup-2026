# Durable per-order canonical accounting

This local journal connects immutable order baselines to the canonical FIFO projection. It has no API or dispatch capability and does not replace the account owner lease, serialized network admission, risk policy or official reconciliation. Use only a restricted runtime directory. No raw responses, headers, credentials or unrelated account fields belong in its input; unknown baseline/receipt fields reject.

Prepare one stable intent, idempotency key, requested terms and attributed pre-order wallet. The journal derives and persists the exact canonical wire body/hash before any dispatch attempt. Record dispatching before I/O. An unknown result remains uncertain; a returned order ID can bind once. Changed preparation, identity or retry payload rejects. An identical-key/body retry can be journaled only from uncertainty; the outer owner must independently authorize it, respect durable backoff and perform the final admission fence. A journal transition never authorizes network traffic.

Every fill report is recalculated from the original immutable wallet. Saved rows cannot disappear or change, canonical terms cannot change, counts cannot regress and timestamps cannot move backward. Repeated identical evidence returns the saved projection without adding a row. A partial projection is not a new baseline. Terminal projections cannot reopen or gain another fill; conflicting later evidence requires account reconciliation rather than silent alteration. Terminal does not mean reconciled or safe to release execution ownership.

The append-only hash chain binds selected payloads, recomputed state hashes and source-code hashes. Restart fully replays every projection. A writer lock, file identity, byte hash, source identity, STOP checks, full writes and fsync fence mutation. A persistence failure marks the live writer uncertain and blocks further updates; restart can replay a complete appended event exactly once, while partial/corrupt records fail without automatic repair. A replaced lock is preserved for investigation. Read-only open never repairs or writes.

This component deliberately has no whole-account adoption or cross-market cash authority. A paired controller must use a shared cash ledger/one active intent, fresh complete signed positions and open orders, source-bound fills and exact acknowledgement money, and complete account/collateral reconciliation before applying its projected wallet. Unknown REST NO prices and non-null ALL collateral remain rejected by the FIFO projection. Tests establish these accounting/durability properties, not profitability or live API compatibility.
