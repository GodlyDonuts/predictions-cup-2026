# Bounded worker scheduling — October 15

Task [#135](https://github.com/GodlyDonuts/predictions-cup-2026/issues/135), Viserion/bounded-scheduling-20261015. NEW dependency-free helper `moloch/live-runtime/src/scheduling.rs`; root retains `worker.rs`, `lib.rs`, production, and account ownership. This candidate does not modify a runtime until integrated and checked. It makes no profitability claim.

## Observed problem versus implementation

Root's V18 observation identified repeated expensive new-order preflights inside one dispatch call, including candidates later rejected by native/authority guards. One physical write per pass did not bound unsuccessful six-GET snapshot attempts. Current source also drains a continuously supplied channel without a work budget. A single broadcast can expand into 237 book events. A frame-count cap alone therefore does not bound durable native admissions. A managed31 packet can postpone the next owned full-fill-tape reconciliation.

These are execution latency risks, not proof that increasing turnover is profitable. Existing receipt times, source freshness, native activation/expiry, STOP, durable unknown acceptance, account limits, and exact financial authority remain unchanged.

## First integration: one expensive preflight per dispatch pass

Import `PreflightBudget`; instantiate it once at entry to each `dispatch` call. Immediately BEFORE the first expensive new-order snapshot packet, call `try_start()`. If false, return from dispatch to the main loop. Consume the permit even when snapshot acquisition, final activation, exact native intent checks, or authority later defer the candidate. Never reset it inside the candidate loop. This bounds expensive attempt count to one; it does not change cancellation or owned reconciliation. Root's current packet may contain seven GETs after adding exact account cash: the permit bounds packets, not a hardcoded number of GETs.

Returning after a failed preflight is also sufficient for this first integration if there is only one snapshot entry point. Neither approach permits stale snapshot reuse. A persistent candidate cursor (or confirmed native retirement of rejected candidates) must move past a failed candidate across calls; always restarting at an unchanged first candidate would still starve later candidates. The test illustrates a persistent cursor and one failed/one successful candidate across two passes. Reset the permit only at the next dispatch pass, with new financial snapshots.

## Ordered draining integration contract

1. Add `mod scheduling` in the runtime library after review; keep a single `OrderedDrain<serde_json::Value>` for the lifetime of the worker's stream/source pair. Do not recreate it at each call.
2. Replace the unbounded receive loop with `drain`. The guard checks current stream health AND current STOP controls. Parse one `Incoming` at a time using the existing recorder/universe observations and `source.broadcast`; Failed/Joined remain fatal. Apply each derived event through the existing durable `accept` operation. `Empty` requires a connected, healthy stream; disconnected is fatal.
3. Budgets are checked before receiving a frame or starting another native admission. Default limits: 32 received frames, 64 admitted native events, 50 monotonic milliseconds per call. Empty-event frames count. No speculative `try_recv` after a budget yield. A pending event is removed only after durable admission succeeds.
4. A broadcast's derived events remain ordered in `OrderedDrain` across calls. Do not parse a later broadcast, call REST `source.accept`, or dispatch quotes while derived events remain pending: `RestSource.broadcast` has already updated parsing state for the whole current frame. Service STOP and independent owned-order reconciliation, then resume these pending events promptly. Do not perform one expensive reconciliation after every 64 events unless the periodic schedule is due.
5. A yield with zero pending derived events is a frame boundary, not proof the receiver is empty. The original worker may interleave REST at a completed frame boundary only under its existing source sequence rules. Never claim a fresh/empty stream merely because a budget expired. If integration instead requires completely empty receiver before any other work, continuous arrivals can starve ordinary source/dispatch; that is not what this helper promises.
6. A parser or durable admission error returns immediately. Do not catch and retry an uncertain durable application: normal fatal/restart recovery applies. `apply` failure retains the front event but does not certify replay safety. A parser error has consumed that input frame and requires fail-closed shutdown. Retain the same stream/session pair while yielding; a reconnect must use existing full source recovery, not silently discard pending events.

The wall-time cap is cooperative. One frame parse, guard check, or one atomic durable event can exceed 50ms; no work already started is interrupted. Pending storage is one parsed frame's derived events, not a fixed memory bound. `source.broadcast` constructs that frame's vector before the helper can yield; this patch does not bound inbound receiver memory or parsing a maliciously large frame. Existing input-size/transport controls remain necessary. Timekeeping here never replaces original source/receipt timestamps or extends their financial eligibility.

## Periodic reconciliation integration contract

Create `ReconciliationSchedule::new(10_000)` and supply monotonic elapsed milliseconds (not wall UTC) for scheduling only. Build `PendingVersion` from durable `DispatchLog.acknowledgments.len()` and `closed.len()`, converting counts safely. Both maps must remain append-only during this schedule's lifetime. ACK count and terminal count detect a changed pending membership even when pending count stays constant. A log reset/replacement requires resetting the schedule to startup, which blocks submissions until reconciliation.

Check `due` at startup, between every selected scope, after draining a budget, and before entering dispatch. On a successful real owned reconciliation call `completed` with time of completion, the durable version AFTER terminal updates, and its CURRENT `blocks_new_submissions`. The latest block replaces earlier permission in both directions; do not retain the first cycle's stale bool. On error do not call completed. Clock/count regression is fatal. Check `permits_submission` again before dispatch and after a new ACK changes the durable version. This scheduling permission is additional to existing fresh ProductionAuthority and shared queue/unknown-acceptance gates; it is never execution authorization.

Completion anchors the interval. A reconciliation taking longer than 10s does not demand an immediate identical cohort and starve all other work. It also does not certify every receipt in that cohort as fresh: existing per-member freshness, exact-order fallback, full-tape validation, durable credits, and cancellation fences remain authoritative. A zero-pending result is not evidence that foreign orders or global unknowns are absent. A REST scope or one preflight can still overrun a deadline; the next boundary must reconcile rather than extend any financial freshness window.

## Scope ordering and fairness

Run `prioritize_selected` only on the vector returned by the existing Universe selection. Pass actual-owned exchanges, plus an explicitly identified urgent SUBSET of actual-owned exchanges. Output is a stable partition: urgent owned, remaining owned, discovery. It never adds/removes scopes, advances a cursor, or increases the original three discovery slots. Unknown urgency cannot invent a selected scope. Duplicate selected scopes and unowned urgent IDs are rejected.

Retain the selected vector and its progress cursor across cooperative yields. Resume the unfinished tail before selecting again; repeatedly dropping the tail and calling Universe.select would defeat its round-robin fairness. This helper does not invent urgency or alter native policy. Mere speculative quotes are not proof of actual account ownership.
